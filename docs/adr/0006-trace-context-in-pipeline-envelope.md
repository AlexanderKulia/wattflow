# Trace context travels in a pipeline envelope, not on the Reading

Channel handoffs between stages aren't function calls, so OTel's normal `context.Context`-through-the-call-chain propagation doesn't apply for free. Each Reading is wrapped in a small envelope (Reading + trace/span context) that travels through every channel; each stage extracts the context, starts its own span for stage latency, and re-attaches before forwarding. This keeps Reading itself as pure domain data — exactly the fields SPEC defines (device_id/timestamp/reading_id/kWh) — while tracing plumbing stays a separate, pipeline-only concern. Alternative considered: restructure stages as direct function calls instead of channels so context.Context propagates natively — rejected, since channels are the chosen transport (ADR-0001) and bounded-channel backpressure (ADR-0002) depends on that shape.
